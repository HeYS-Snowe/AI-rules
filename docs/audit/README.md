# 项目审计系统 (Project Audit System)

> 定期审计的项目健康待办池 — 批量发现、批量处理"文档同步、git 卫生"这类小事情。
> 创建日期: 2026-07-10 | 存储位置: `D:\Code\.Rules\docs\audit\`

---

## 定位

本系统记录**定期扫描各业务项目时发现的健康待办**——版本号矛盾、文档过时、git 未提交、未纳入版本控制等问题。

- **轻量**：聚焦"小事情"，不替代正式的 bug 追踪或需求管理
- **定期**：作为周期性任务执行（手动触发或 `/loop`），每次产出一批待办
- **可操作**：每条都是明确的、可在一两次会话内处理完的行动项

### 与其他系统的边界

| 系统 | 存什么 | 给谁 | 位置 |
|------|--------|------|------|
| `ERROR/` | AI 的**跨项目经验 / 行为纠正** | AI（跨会话学习） | `D:\Code\.Rules\ERROR\` |
| 项目 `.issues/` | 项目自身的 **bug**（代码缺陷） | 团队（随项目走） | 各项目根 `.issues/` |
| **本项目审计** | 扫描发现的**项目健康待办**（文档/git/版本等） | 单人开发者批量处理 | `D:\Code\.Rules\docs\audit\` |

> 三者职责分离、NEVER 双写。审计发现的是"维护卫生"问题，不是代码 bug（归 `.issues/`），也不是 AI 行为纠正（归 `ERROR/`）。

## 命名规则

```
{标题关键字，多个用_分隔}-{YYYYMMDD}-{等级}.md
```

| 段 | 规则 | 示例 |
|----|------|------|
| 标题关键字 | 小写英文，多个词用 `_` 分隔，概括问题 | `version_mismatch` / `uncommitted_files` / `no_version_control` |
| 日期 | 扫描/存储日期 `YYYYMMDD` | `20260710` |
| 等级 | `P0` / `P1` / `P2` / `P3`（见下表） | `P1` |

**示例**：`version_mismatch-20260710-P1.md`、`git_no_history-20260710-P1.md`

- 同一问题重复扫描到：**更新原条目**（补证据、刷新日期、必要时升等级），NEVER 新建重复文件 — 原因：去重优先，避免待办池膨胀
- 问题解决后：将 `status` 改为 `resolved` 并填 `resolved` 日期，文件保留作历史，不删除

## 等级体系（P0–P3）

> 等级决定 agent 处理优先级与主动程度。

| 等级 | 含义 | 触发场景 | agent 行为 |
|------|------|----------|-----------|
| **P0** | 危险 / 阻塞 | 数据可能丢失、安全风险、构建不可用 | 本会话立即处理，并主动提醒用户 |
| **P1** | 高 | 影响正确性或协作：文档矛盾、git 状态异常、活跃项目无版本控制 | 本会话内优先处理，或强烈建议用户处理 |
| **P2** | 中 | 应处理但不紧急：未提交文件、文档小幅过时 | 下次相关会话时处理 |
| **P3** | 低 | 改善项：停滞项目入 git、命名清理 | 有空时处理，定期批量清理 |

## 条目格式

```markdown
---
title: 问题标题（中文，简洁）
project: 项目英文名（与目录名一致）
level: P0 | P1 | P2 | P3
category: docs-sync | git-hygiene | version | structure | dependency | config
status: open | resolved
found: YYYY-MM-DD
resolved:                # 解决后填日期，未解决留空
---

## 问题描述

一两句话说清是什么问题。

## 证据

客观事实（扫描输出、文件路径与行号、命令结果），NEVER 主观推断。

## 建议

可执行的处理步骤，给到具体命令或文件。

## 解决记录

<!-- 解决后填写：做了什么、何时、由谁确认 -->
```

### 分类（category）

| 分类 | 说明 |
|------|------|
| `docs-sync` | 文档与实际不同步（CLAUDE.md / README 过时） |
| `git-hygiene` | git 卫生（未提交、未 init、无历史、分支混乱） |
| `version` | 版本号矛盾或不规范 |
| `structure` | 目录结构偏离规范 |
| `dependency` | 依赖问题（过时、冗余、缺失） |
| `config` | 配置问题（环境变量、构建配置） |

## 定期审计流程

```
触发审计（手动"扫描项目状态" / /loop 定时）
  │
  1. 逐项目采集信号：git log、git status、关键文件改动时间、CLAUDE.md 与实际一致性
  │
  2. 识别待办 → 只记录"需要行动"的项，正常状态不入库
  │
  3. 按项目写入条目：已存在则更新，新问题则新建
  │
  4. 同步 PROJECTLIST.md 的「扫描备注」作为全局索引
  │
  5. 用户/agent 批量处理 → 处理完标 resolved
```

- **NEVER 把"项目正常"也记成条目** — 原因：审计池只放待办，正常状态在 `PROJECTLIST.md` 状态列体现
- 全局快照与跨项目观察写在 `PROJECTLIST.md` 的「扫描备注」，NEVER 在 audit 内重复 — 原因：单一事实来源

## AI 查阅约定（规则）

> 本约定是 audit 机制生效的关键。建议提升到 `common/core/workflow.md` 作为正式规则（本文档先定义）。

**进入任何业务项目会话时，AI 应：**

1. 检查 `D:\Code\.Rules\docs\audit\{项目名}\` 是否存在未处理（`status: open`）条目
2. 按 level 排序，P0/P1 项**主动告知用户**并建议本会话处理
3. 处理完成后，将对应条目标记 `resolved` 并填日期

- 这条约定一处定义、全局生效，NEVER 在每个项目 CLAUDE.md 重复 — 原因：DRY，改一次而非改 N 次
- 若某项目有特殊审计需求，再在该项目 CLAUDE.md 追加项目特定规则
