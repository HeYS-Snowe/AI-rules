## 一、协作谱系（蜂巢 vs 雁阵）

| 维度 | 蜂巢（集群） | **雁阵（本规范）** |
|------|--------------|---------------------|
| 规模 | 几十上百个 Agent 同时作业 | **2 个及以上少量 Agent** |
| 分工 | 同一任务切细粒度并行扇出 | 组长/组员、项目经理/项目组式的分工接力 |
| 典型 | 子代理编排、大规模重构扇出 | Claude Code + Codex 协作同一项目，按阶段/文件边界轮换 |
| 协调成本 | 靠编排器/任务图 | 靠**状态源文件 + 所有权登记**（本规范核心） |
| 失效模式 | 任务图错了全盘错 | 状态漂移、互相覆盖、架构分叉——本规范防的就是这三个 |

**判定**：≤ 5 个 Agent 接力/分工同一项目 → 雁阵（用本规范）；大规模扇出 → 蜂巢（用编排工具自身的任务图机制，本规范的状态源原则仍可借鉴）。

## 二、潮汐调度策略（费率错峰）

**背景**：不同 Agent 接入的 API / coding plan 计费策略不同——部分为峰谷定价，高峰时段消耗翻倍甚至数倍。

**策略**：把"哪个时段/哪类任务用哪个 Agent"当作调度问题——

```yaml
错峰原则:
  - 高峰时段: 优先使用无峰谷定价的 API/Agent，或按谷价计费的通道
  - 谷价时段: 集中跑高消耗任务（大规模重构/长测试循环/批量生成）
  - 混合排程: 重活排给谷价通道，轻活/紧急活排给平价通道

调度决策顺序:
  1. 任务的消耗画像（预估 token 量/时长）
  2. 当前时段各通道的计费状态（峰/谷/无峰谷）
  3. Agent 能力匹配度（能力差距 < 计费差 → 选便宜的；能力硬门槛优先）
  4. 上下文连续性（接力成本：新 Agent 需要读状态源重建上下文，小任务不值得换）

NEVER:
  - NEVER 为了省费用把能力硬门槛低的 Agent 排进关键路径（返工成本 > 差价）
  - NEVER 在状态源不完整时切换 Agent（接手方重建上下文的消耗可能吃掉全部节省）
```

## 三、状态源铁律（HANDOFF-CURRENT）

多个 Agent 协作同一项目时，**必须存在唯一当前状态源文件**（惯例命名 `docs/HANDOFF-CURRENT.md`）：

```yaml
铁律:
  - 唯一性: 当前状态只有一个权威来源；历史交接文件仅作追溯快照，NEVER 用其判断当前任务
  - 接手前三步（不做完不得动工）:
      1. 读状态源 + 项目规则文件（CLAUDE.md / AGENTS.md）
      2. git status --short --branch 实测，核对状态源记载的基线/分支/未跟踪文件——不一致先更新状态源
      3. 对将修改的文件登记或核对所有权
  - 原子更新: 开始/完成/暂停/移交一个工作项时，实施方必须当场更新状态源（HEAD、阶段、已完成/未完成、所有权、下一动作、阻塞）
  - 核验记录: 状态源内维护核验表（时间 | 智能体 | 动作与验证），每次接手/交接留痕
  - 实测优先: HEAD hash、分支领先数、测试结果一律以命令实测为准，NEVER 沿抄上一手记载（实证：Trace 曾有 hash 笔误 35d85fd→4018864，靠实测核正）
```

## 四、文件所有权登记

```yaml
规则:
  - 多 Agent 并行时，每个在途工作项必须登记文件所有权（预期文件边界，写入状态源）
  - 另一 Agent 占用该文件或工作区存在相关未提交改动 → 不得覆盖，先交接或拆分文件边界
  - 边界变更必须先在状态源登记再动工
  - 未登记即改 = 侵权，发现的回滚并登记
```

## 五、三态标注（诚实措辞）

工作项状态只允许三态，状态源与汇报中 NEVER 混用：

| 三态 | 含义 | 反例（禁止的措辞） |
|------|------|---------------------|
| **原型** | demo/POC 存在，未进正式实现 | 把"已写原型"说成"已实现" |
| **已实现** | 代码进了正式路径 | 把"测试应当会通过"说成"已验证" |
| **已验证** | 验证命令实际跑过且通过（命令与结果写入状态源） | 把"已讨论"当作任何一种实现状态 |

> 与 §一.3 如实汇报、§一.18 验收三层同源：三态是它们在多智能体场景的具体化——因为接手方只能依赖状态源的文字，措辞失真 = 污染唯一状态源。

## 六、交接三清单

每次移交/暂停，状态源必须写清三份清单（与单智能体场景的"进度交付三件事"同构）：

1. **下一动作清单** —— 接下来要干嘛（谁、做什么、预期文件边界）
2. **等待/阻塞清单** —— 等什么（用户验收？外部依赖？）、禁止并行的项（防止架构/数据模型分叉）
3. **差距清单** —— 还差什么（未完成项、未跑的验证、待推送的提交）

## 七、适用与禁止

```yaml
适用:
  - 同一项目 2~5 个 Agent 接力/分工（雁阵标准形态）
  - 跨工具接力（CC → Codex → OpenCode …）——交接时状态源是唯一可靠的上下文载体
  - 峰谷计费环境下的时段调度

禁止:
  - NEVER 无状态源多 Agent 并行（必然互相覆盖或分叉）
  - NEVER 两个 Agent 同时持有同一文件的所有权
  - NEVER 用对话记忆替代状态源（新会话/新工具读不到你的对话）
  - NEVER 跳过接手三步直接动工
```
