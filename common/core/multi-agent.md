# 多智能体协作规范 —— 潮汐雁阵 Tidal Echelon

> 创建：2026-09-14 | 首发实践：Trace 项目双智能体协作（Claude Code + Codex，提交 `4018864`）
> 命名：用户命名资产——模式名「雁阵 Echelon」、策略名「潮汐调度」、完整名「潮汐雁阵 Tidal Echelon」
> 适用：同一项目由两个及以上 Agent 工具（CC / Codex / OpenCode / Qoder / deepcode 等）接力或并行开发的一切场景

---

## 一、协作谱系（蜂巢 vs 雁阵）

| 维度 | 蜂巢（集群） | **雁阵（本规范）** |
|------|--------------|---------------------|
| 规模 | 几十上百个 Agent 同时作业 | **2 个及以上少量 Agent** |
| 分工 | 同一任务切细粒度并行扇出 | 组长/组员、项目经理/项目组式的分工接力 |
| 典型 | 子代理编排、大规模重构扇出 | Claude Code + Codex 协作同一项目，按阶段/文件边界轮换 |
| 协调成本 | 靠编排器/任务图 | 靠**状态源文件 + 所有权登记**（本规范核心） |
| 失效模式 | 任务图错了全盘错 | 状态漂移、互相覆盖、架构分叉——本规范防的就是这三个 |

**判定**：≤ 5 个 Agent 接力/分工同一项目 → 雁阵（用本规范）；大规模扇出 → 蜂巢（用编排工具自身的任务图机制，本规范的状态源原则仍可借鉴）。

## 二、潮汐调度策略（费率错峰）

**背景**：不同 Agent 接入的 API / coding plan 计费策略不同——部分为峰谷定价，高峰时段消耗翻倍甚至数倍。

**策略**：把"哪个时段/哪类任务用哪个 Agent"当作调度问题——

```yaml
错峰原则:
  - 高峰时段: 优先使用无峰谷定价的 API/Agent，或按谷价计费的通道
  - 谷价时段: 集中跑高消耗任务（大规模重构/长测试循环/批量生成）
  - 混合排程: 重活排给谷价通道，轻活/紧急活排给平价通道

调度决策顺序:
  1. 任务的消耗画像（预估 token 量/时长）
  2. 当前时段各通道的计费状态（峰/谷/无峰谷）
  3. Agent 能力匹配度（能力差距 < 计费差 → 选便宜的；能力硬门槛优先）
  4. 上下文连续性（接力成本：新 Agent 需要读状态源重建上下文，小任务不值得换）

NEVER:
  - NEVER 为了省费用把能力硬门槛低的 Agent 排进关键路径（返工成本 > 差价）
  - NEVER 在状态源不完整时切换 Agent（接手方重建上下文的消耗可能吃掉全部节省）
```

## 三、状态源铁律（HANDOFF-CURRENT）

多个 Agent 协作同一项目时，**必须存在唯一当前状态源文件**（惯例命名 `docs/HANDOFF-CURRENT.md`）：

```yaml
铁律:
  - 唯一性: 当前状态只有一个权威来源；历史交接文件仅作追溯快照，NEVER 用其判断当前任务
  - 接手前三步（不做完不得动工）:
      1. 读状态源 + 项目规则文件（CLAUDE.md / AGENTS.md）
      2. git status --short --branch 实测，核对状态源记载的基线/分支/未跟踪文件——不一致先更新状态源
      3. 对将修改的文件登记或核对所有权
  - 原子更新: 开始/完成/暂停/移交一个工作项时，实施方必须当场更新状态源（HEAD、阶段、已完成/未完成、所有权、下一动作、阻塞）
  - 核验记录: 状态源内维护核验表（时间 | 智能体 | 动作与验证），每次接手/交接留痕
  - 实测优先: HEAD hash、分支领先数、测试结果一律以命令实测为准，NEVER 沿抄上一手记载（实证：Trace 曾有 hash 笔误 35d85fd→4018864，靠实测核正）
```

## 四、文件所有权登记

```yaml
规则:
  - 多 Agent 并行时，每个在途工作项必须登记文件所有权（预期文件边界，写入状态源）
  - 另一 Agent 占用该文件或工作区存在相关未提交改动 → 不得覆盖，先交接或拆分文件边界
  - 边界变更必须先在状态源登记再动工
  - 未登记即改 = 侵权，发现的回滚并登记
```

## 五、三态标注（诚实措辞）

工作项状态只允许三态，状态源与汇报中 NEVER 混用：

| 三态 | 含义 | 反例（禁止的措辞） |
|------|------|---------------------|
| **原型** | demo/POC 存在，未进正式实现 | 把"已写原型"说成"已实现" |
| **已实现** | 代码进了正式路径 | 把"测试应当会通过"说成"已验证" |
| **已验证** | 验证命令实际跑过且通过（命令与结果写入状态源） | 把"已讨论"当作任何一种实现状态 |

> 与 §一.3 如实汇报、§一.18 验收三层同源：三态是它们在多智能体场景的具体化——因为接手方只能依赖状态源的文字，措辞失真 = 污染唯一状态源。

## 六、交接三清单

每次移交/暂停，状态源必须写清三份清单（与单智能体场景的"进度交付三件事"同构）：

1. **下一动作清单** —— 接下来要干嘛（谁、做什么、预期文件边界）
2. **等待/阻塞清单** —— 等什么（用户验收？外部依赖？）、禁止并行的项（防止架构/数据模型分叉）
3. **差距清单** —— 还差什么（未完成项、未跑的验证、待推送的提交）

## 七、适用与禁止

```yaml
适用:
  - 同一项目 2~5 个 Agent 接力/分工（雁阵标准形态）
  - 跨工具接力（CC → Codex → OpenCode …）——交接时状态源是唯一可靠的上下文载体
  - 峰谷计费环境下的时段调度
  - 主从编排（头雁制）：强模型编排+其余执行，派遣记录入状态源（§九）

禁止:
  - NEVER 无状态源多 Agent 并行（必然互相覆盖或分叉）
  - NEVER 两个 Agent 同时持有同一文件的所有权
  - NEVER 用对话记忆替代状态源（新会话/新工具读不到你的对话）
  - NEVER 跳过接手三步直接动工
  - NEVER 编排者亲自执行（角色分离，§九）；NEVER 模型自填派遣时间戳（必须命令实测到秒）
```

## 九、主从编排（头雁制）与派遣记录

> 2026-11-03 新增（用户提出）。背景演化：雁阵最初为解决额度不足（§二 潮汐调度省钱）；额度充足后演化出主从协同——强模型做编排（拆解/派遣/验收），其余执行。"头雁制"为候选名，命名权在用户。

### 编制三型（阵型）

| 阵型 | 结构 | 适用 |
|------|------|------|
| 接力 | 对等，按阶段轮换交接 | 单线程长任务 |
| 并行分工 | 对等，按文件边界同时干 | 独立模块（所有权登记管边界） |
| **主从编排** | 1 个编排者 + 1~N 个执行者 | 任务可拆、需要统一决策与验收 |

### 角色分工

- **编排者（头雁）**：拆任务、写派遣记录、验收产出、维护状态源工作项与编制画像。NEVER 亲自执行——角色分离，防"把好活留给自己/把模糊任务踢给执行者"。
- **执行者**：只做被派遣任务包内的事；完成即回写状态源（§三 原子更新不变）；遇超出任务包的事（相邻 bug/需求矛盾/验收标准做不到）停下回写阻塞，由编排者裁决，NEVER 自行扩权。

### 派遣记录（状态源必备小节）

| 时间（实测到秒） | 派遣 → 执行 | 任务 | 状态 |
|------|------|------|------|
| 2026-11-03 14:32:05 | 编排(Codex/GPT-6.1 Sol) → 执行(CC/GLM-5.3-Flash) | #W3 实现登录接口 | 已派遣 |

```yaml
铁律:
  - 时间戳命令实测: 用 date '+%Y-%m-%d %H:%M:%S' 取真实时间，NEVER 模型自填——模型没有真实时钟，自填即编造（§三 实测优先的具体化）
  - 派遣即登记: 登记与派遣同轮发生，NEVER 先派出去回头补记录
  - 回执对称登记: 执行者完成时补一行回执（时间/执行者/三态结果/验证命令），派遣-回执成对形成完整链路
```

### 任务包五件套（编排者每次派遣附带）

1. **目标**——一句话说清要什么（给目标不给实现步骤，对齐 §一.20 方向由目标决定）
2. **验收标准**——怎么算完成；"已验证"必须命令实测（§五 三态）；**按影响停止**（2026-11-03 借鉴 dsh-superagent）——本地改动推进到可评审的结果为止，需要设计决策就带着具体问题停，NEVER 为"看起来做完"而自行拍板
3. **文件边界**——所有权预登记（§四）
4. **并行声明**——与哪些在途任务并行安全/不安全
5. **回传要求**——完成后在状态源写什么

### 已知弱点与自防

- **编排者单点**：编排者的任务队列与各执行者状态写入状态源"编制画像"小节——编排者本身可接力（新会话/新工具接管重建）
- **粒度失控**：任务包过细=执行者沦为打字员（浪费），过粗=理解偏差（返工）——粒度=一个有验收标准的工作项
- **集成断裂**：并行执行者互不知对方接口变更——并行声明 + §六"禁止并行项"清单强制编排者裁决

## 十、拉起与通讯（无人值守）

> 2026-11-03 新增。解决：编排者如何在用户不在场时拉起执行者并保持通讯。前提修正：心跳机制在无人值守场景下必要（本节发布前的"人在盯"前提不成立，用户指出）。

### 使用偏好 ≠ 拉起方式（2026-11-03 用户澄清）

- **日常人工操作**：有 Desktop 先用 Desktop，没有再用 CLI——唯一例外 CC：用户偏好 CC 的 CLI（自认为比 Desktop 好用，自称可能有偏见）
- **无人值守拉起**：走 CLI 内核（矩阵见下）——Desktop 与 CLI 是同一 agent 的两个入口（一个大脑两扇门），CLI 拉起不违背"日常用 Desktop"的偏好；被拉起干完的活，用户回来照常在 Desktop 里继续

### 执行者两类与拉起矩阵

| 类型 | 代表 | 首选拉起 | 兜底 |
|------|------|----------|------|
| CLI | CC / Codex CLI / deepcode / dsh headless | 编排者进程直调：`claude -p "<任务包>"`、`codex exec`、`dsh --profile headless "<任务包>"`——stdin 传任务、stdout 收结果 | 任务文件 + 守护脚本轮询拉起（见心跳） |
| CLI 常驻（推荐） | CC 双向流：`claude -p --input-format stream-json --output-format stream-json`（2026-11-03 实测：stdin 持续派任务、stdout 实时出过程，进程不退、上下文连续） | 常驻执行者，编排者写一行 JSONL 即派遣；围观用 transcript tail 或 stdout 滚屏 | 每次派 `-p` 新进程（启动开销+无上下文） |

> 注：向"已打开的交互式 TUI 窗口"注入任务在 Windows 下无干净通道（stdin 挂在终端 conpty 上，无 tmux send-keys 等价物；窗口按键模拟仅兜底）——常驻双向流是"已开着的 CC 被编排者直接指挥"的官方正解。CC↔CC 另有 Remote Control 会话互发机制（编排者为 CC 时可用）。
| Electron 桌面端 | Codex 桌面版 / dsh desktop | **优先找等价 CLI 入口**——Electron 只是 GUI 壳，多数自带 CLI 内核（Codex 桌面 ↔ `codex exec`；dsh desktop ↔ `dsh --profile headless`） | GUI 自动化（剪贴板注入+窗口激活，脆弱，仅应急）；通知器叫人（toast/响铃） |

**拉起模式（2026-11-03 用户定则：全用心跳机制统一）**：

- **心跳（pull，唯一默认）**——所有执行者统一走 `docs/dispatch/` 轮询认领：编排者写任务包文件 → 执行者侧守护脚本轮询 → 拉起干活 → 写回执。不依赖任何 GUI 同步、会话归组或双向流管道——真相只在文件（§三 状态源铁律）
- **直调与注入降为可选优化**：`codex exec` / `dsh --profile headless` 单发、CC 双向流常驻（`--input-format stream-json`，2026-11-03 实测可用）——仅当编排者与执行者同机且需要低延迟时手动使用，非默认路径
- **实证背景（2026-11-03）**：dsh headless 会话在桌面版**不实时出现**，且**永远落"未分组"**（分组表 workspace.json 由桌面版 UI 维护，headless 不登记，cwd 在哪都一样）——GUI 围观不可依赖，文件总线是唯一可靠通道

### 通讯（文件总线为正道）

1. **文件总线（默认）**：编排者把任务包写为 `docs/dispatch/<ID>.md` → 执行者读包干活 → 完成写 `docs/dispatch/<ID>.receipt.md` 并更新状态源。全程落盘：跨工具、无人值守、可追溯（§三 状态源铁律的自然延伸）
2. **CLI 直调管道**：编排者进程调用执行者时 stdin/stdout 即通讯管道，结果由编排者代写回执与状态源
3. **剪贴板桥（GUI-only 过渡）**：脚本写剪贴板 + toast 通知，人只按 Ctrl+V 与回车——半自动，非终态

### 心跳（守护脚本实体化）

> 心跳是**唯一默认拉起机制**——守护脚本是雁阵的必需组件，不是可选件：没有它，无人值守的执行者不会被拉起。
>
> **注意力预算**（2026-11-03 借鉴 dsh-superagent）：每条通知/toast 都要"价值 > 注意力成本"——toast 只在"必须人动"时响（拉起失败/无回执/超时），例行事件只进审计日志不弹窗；健康状态不占人注意力。

- **执行者心跳**：轮询 `docs/dispatch/` 发现未认领任务包 → 按包内指定的执行者类型拉起
- **编排者心跳**：轮询回执文件/状态源变更 → 验收、派发下一批
- **实体**：一个守护脚本（计划任务或后台常驻，实现落于 `.AI-TOOLS\Scripts`）——本节定机制，脚本另行落地

### 安全闸（无人值守 = 权限放大）

- 无人值守执行者的可写范围限本项目内；NEVER 无人值守执行不可逆操作（部署/发布/迁移/批量删除）——此类任务只允许"打包待办"，回队由用户拍板（§一.11 两手准备）
- 执行者拉起命令必须带受限权限参数（如 CC 的 permission mode / dsh 的 sandbox），NEVER 无沙箱全权放跑
- **影子模式**（2026-11-03 借鉴 dsh-superagent）——无人值守的主动工作先跑"只记录"阶段：执行者写出"我会做什么"而不真执行，人看过记录并认可后才开始真执行；信任逐步放大，NEVER 一步放权到位
