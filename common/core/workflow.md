## 三、编码实现阶段

### 3.1 开发流程

```yaml
分支策略:
  main: 生产环境，受保护
  develop: 开发环境
  feature/*: 功能分支
  fix/*: 修复分支
  release/*: 发布分支

开发步骤:
  1. 从 develop 创建 feature 分支
  2. 编写代码 + 单元测试
  3. 自检代码质量
  4. 提交 Pull Request
  5. 代码审查
  6. 合并到 develop
```

### 3.2 提交规范

```yaml
格式: <type>(<scope>): <subject>

类型 (type):
  - feat: 新功能
  - fix: Bug 修复
  - refactor: 重构
  - style: 代码格式
  - docs: 文档
  - test: 测试
  - chore: 构建/工具
  - perf: 性能优化

示例:
  - feat(auth): add JWT token refresh
  - fix(api): resolve timeout issue in user service
  - refactor(user): extract validation logic
  - docs(readme): update installation guide
```

### 3.3 变更后自动测试

AI 在执行以下操作后，**必须自动运行测试**以验证功能正常：

```yaml
触发条件:
  - 修改了源代码文件
  - 修改了配置文件 (可能影响运行时行为)
  - 修改了依赖版本
  - 重构了代码结构
  - 修复了 Bug
  - 任何可能影响已有功能的操作

测试范围:
  直接测试:
    - 被修改的功能/模块
    - 新增的代码路径
    - 修复的 Bug 对应场景

  关联测试:
    - 调用被修改代码的上游功能
    - 被修改代码依赖的下游模块
    - 与修改涉及同一数据模型的模块
    - 与修改涉及同一 API 接口的调用方

执行要求:
  1. 识别变更影响范围
  2. 运行直接相关的测试
  3. 运行关联功能的测试
  4. 全部通过后才视为变更完成
  5. 若测试失败，立即修复，不可跳过
```

### 3.4 AI 行为约束

> AI 在执行开发任务时必须遵守的行为边界

```yaml
工具使用:
  - 使用专用工具而非通用命令行（专用工具有操作记录）
  - NEVER 用 bash cat/echo 读取文件 — 用 Read 工具
  - NEVER 用 bash sed/awk 编辑文件 — 用 Edit 工具
  - NEVER 用 bash find/ls 搜索文件 — 用 Glob 工具
  - NEVER 用 bash grep/rg 搜索内容 — 用 Grep 工具
  - Windows 下执行 PowerShell 命令一律用 pwsh（PowerShell 7.6.4，首选），NEVER 用 powershell（5.1，仅作备用）

  原因: 专用工具有操作记录和审计追踪，通用命令行是黑箱操作
  （pwsh 原因: Windows 自带 powershell 为 5.1 旧版，默认 GBK 编码，中文注释/脚本易乱码；pwsh 7.x 默认 UTF-8，兼容性更好）

授权边界:
  - 用户对某操作的授权仅限当前上下文，NEVER 自行扩大范围
  - 影响共享系统的操作（push、部署、删除）必须先确认
  - NEVER 一次性授权视为永久授权

  原因: 用户的一次性信任不等于对同类操作的永久授权

先看再改:
  - NEVER 在未读取文件内容的情况下编辑或建议修改
  - 修改前必须理解现有代码的意图和上下文
  - 编辑他人代码时，先理解设计意图再动手

  原因: 不看就改是引入 bug 的最高效方式
```

### 4.2 测试结构 (AAA 模式)

```dart
test('getUser returns user when user exists', () async {
  // Arrange - 准备
  final mockRepository = MockUserRepository();
  final service = UserService(mockRepository);
  const userId = 'user-123';
  final expectedUser = User(id: userId, name: 'John');

  when(mockRepository.findById(userId))
      .thenAnswer((_) async => expectedUser);

  // Act - 执行
  final result = await service.getUser(userId);

  // Assert - 断言
  expect(result, equals(expectedUser));
  verify(mockRepository.findById(userId)).called(1);
});
```

## 五、构建打包阶段

### 5.1 构建流程

```yaml
环境检查:
  - 依赖版本正确
  - 环境变量配置
  - 构建工具可用

构建执行:
  - 清理旧产物
  - 编译/打包
  - 资源优化
  - 代码混淆 (Release)

产物命名:
  # 通用格式（使用 - 分隔符）
  格式: "{项目名}-{版本号}-{状态}-{日期}.{ext}"
  # 有依赖时（如前置库、SDK）
  格式_含依赖: "{项目名}-{版本号}+{依赖名}-{依赖版本}-{状态}-{日期}.{ext}"

  版本号:
    格式: "{MAJOR}.{MINOR}.{PATCH}.{BUILD}[.fix{N}]"
    MAJOR: "不兼容的 API 变更"
    MINOR: "向后兼容的功能新增"
    PATCH: "向后兼容的问题修复（增量按修改量映射，见 §5.3）"
    BUILD: "构建序号，每次构建递增 — 区分同日同版本号的产物，防止文件被覆盖，确保每次构建都有独立的产物保留"
    fix: "紧急修复，同 BUILD 版本内的修复次数（仅紧急修复时有此段）"

    示例:
      - "1.0.0.1"        # 首次发布
      - "1.1.0.2"        # 功能更新
      - "1.1.1.3"        # Bug 修复
      - "1.1.1.3.fix1"   # 紧急修复

  状态:
    完全体:
      - release: 正式版
      - fix: 修复版
      - hotfix: 紧急修复

    非完全体:
      - alpha: 内测版
      - beta: 测试版
      - rc: 候选版
      - dev: 开发版
      - debug: 调试版

  示例:
    - "MindCareAI-1.0.0.1-release-20250312.apk"
    - "MindCareAI-1.1.0.2-alpha-20250315.apk"
    - "MindCareAI-1.0.1.3.fix1-hotfix-20250313.apk"
    - "MyApp-2.0.0.4+flutter-sdk-3.22+-release-20250401.apk"
```

### 5.1b builds 目录结构（release / packages 分离）

> **所有项目统一**。开始发布 GitHub Packages（Maven/NuGet/npm 等包管理器产物）后，构建产物必须按
> release（人工/渠道分发）与 packages（包管理器分发）分离存放——单一扁平目录无法同时承载两类分发。

```yaml
builds/ 目录规范:
  release/:                 # 正式分发产物（人工/渠道：APK、IPA、zip 等）
    android/:               #   APK/AAB：{项目}-{版本}-{状态}-{日期}.apk
    ios/:                   #   IPA（如适用）
    windows/:               #   zip/exe（桌面端）
    release_notes/:         #   release_notes_v{版本}.md（Release notes 正文）
    build_history.json      #   构建记录（sha256 / 源路径 / 产物路径）
    release_history.json    #   发布记录（tag / assets / notesFile / status）
  packages/:                # 包管理器分发产物（GitHub Packages 等）——包是跨端的，按包生态划分而非平台
    npm/:                   #   .tgz（JS/TS 共享代码，跨端不分平台）
    maven/:                 #   .aar/.jar + pom（Android 组件坐标）
    nuget/:                 #   .nupkg（.NET/Windows 组件）
    release_notes/:         #   每个包版本的说明 md
  README.md                 # 目录结构规范说明（本文件摘录）

规则:
  - 产物（apk/zip/tgz/aar/nupkg）不入库（.gitignore 忽略产物目录）；入库的只有记录 json、release_notes、README
  - 历史记录（build_history/release_history）中的路径一律写 release/ 前缀，移动目录后同步更新，避免路径失效
  - release 与 packages 命名互不冲突：release 走 §5.1 命名，packages 走包管理器坐标（见 common/core/npm-private-publish.md）
  - packages 不按平台划分（tgz 跨端、Android 是 AAR 坐标、Windows 是 nupkg），按包生态分目录
  - 参考实现：Jeenith 项目 builds/（完整落地案例，git mv 保留历史）
```

### 5.3 编译后版本号推荐

> 每次构建完成后，AI 根据本次改动推荐版本号，由用户确认后用于产物命名。NEVER 未经确认直接修改版本号。

```yaml
触发时机: 每次编译/构建完成后

输入来源:
  - 本次构建所基于的 git 提交记录
  - 本次会话内的代码修改
  - CHANGELOG (Added / Fixed / Changed / Broken)

推断规则:                       # 复用 §5.1 版本号语义
  含不兼容 API 变更: MAJOR + 1
  含向后兼容的新功能: MINOR + 1
  仅向后兼容的问题修复: PATCH 按修改量映射（见下）
  PATCH 增量映射:               # 版本号反映修改量，避免大量改动仅 +1 无法追溯
    修复/变更数量 1 个: PATCH + 1
    修复/变更数量 2-3 个: PATCH + 2
    修复/变更数量 4 个及以上: PATCH + 3
    含重大修复(崩溃/数据丢失/安全问题): 额外 +1
    上限: 单次发布 PATCH 增量最多 +3，不得仅因"改动很多"无限跳号
    依据: 以 git diff / CHANGELOG 实际条目数为准，NEVER 凭感觉估数
  BUILD: 每次构建递增（兜底区分同日同版本号的产物）
  紧急修复: 追加 .fix{N}

输出格式:
  当前版本: "{当前版本号}"
  推荐版本: "{推荐版本号}"
  升级段: MAJOR | MINOR | PATCH
  依据:
    新增(向后兼容):
      - "{改动项}"
    修复(向后兼容):
      - "{改动项}"
    不兼容变更:
      - "{改动项}" 或 "无"
  理由: "{为什么升这一段}"
  待确认: "是否采用 {推荐版本号}？"

执行方式:                       # 推荐 + 确认
  1. AI 输出推荐版本号 + 依据
  2. 用户确认
  3. 确认后的版本号进入 §5.2 产物命名（version-manager 用此号重命名）

禁令:
  - NEVER 未经用户确认直接修改版本号
  - NEVER 在无法判断改动性质时强行推荐 — 须先列明改动并询问
```

示例:

```yaml
当前版本: "1.1.0.3"
推荐版本: "1.2.0.4"
升级段: MINOR
依据:
  新增(向后兼容):
    - 用户头像上传接口
  修复(向后兼容):
    - 登录态偶发丢失
  不兼容变更:
    - 无
理由: "含向后兼容的新功能 → MINOR+1；BUILD 递增"
待确认: "是否采用 1.2.0.4？"
```

## 九、错误记录流程

> 完整记录规范见 `ERROR/README.md`

### 9.1 检索优先

出现问题后，**先检索已有记录**：

```yaml
检索流程:
  1. 搜索 ERROR/entries/ 中是否有相似记录（按类型 + 标签 + 关键词）
  2. 有 → 优先参考其方案，结合当前情况判断是否适用
  3. 无 → 正常解决，解决后自动记录

重要原则:
  - 检索结果仅供参考，不盲从旧方案
  - 环境可能已变化，旧方案未必有效
  - 每次参考后评估：有效→保持 / 已过时→更新或标记 deprecated
```

### 9.2 主动记录触发条件

AI 在以下情况**主动记录**到 `ERROR/entries/`，无需用户指令：

```yaml
触发场景:
  - 用户主动报告的问题
  - 任务执行中的错误（构建失败、测试失败、运行时崩溃）
  - AI 行为被用户纠正（用户说"不对"、"应该是xxx"、"不要xxx"）
  - 排查过程超过 3 步的问题
  - 重复出现的问题（更新已有记录）

不记录:
  - 简单的语法修正（拼写、标点）
  - 用户明确表示不需要记录
```

### 9.3 记录流程

```yaml
步骤:
  1. 解决问题后，判断是否需要记录
  2. 搜索 ERROR/entries/ 是否有相似记录
  3. 有 → 更新（补充新方案、增加 occurrences、更新 last_seen）
  4. 无 → 创建新条目（按 ERROR/README.md 模板）
  5. 更新 ERROR/INDEX.md 索引
  6. 无感执行，不主动告知用户
```

> 错误类型定义（7 类）、条目模板、字段说明详见 `ERROR/README.md`

### 9.4 项目级问题档案 (.issues/)

> 记录项目本身的 bug/问题，随项目走，面向团队/未来维护者。与 §9.1-9.3 的 `ERROR/`（规则库级 AI 经验）职责分离。
> 本行为由**可复用触发机制**驱动：通用流程见 `common/core/trigger-mechanism.md`，本段定义该行为的注册参数。

```yaml
# —— 触发机制注册参数（行为名: 项目 bug 记录）——
交互: 无感执行

触发条件（满足任一即记录）:
  - 用户主动报告的 bug / 问题
  - 任务执行中出现的 bug（功能异常、崩溃、数据错误、回归）
  - 排查过程超过 3 步的问题
  - 修复完成后（记录根因 + 方案，供未来维护者参考）
  - 上述场景首次出现且 .issues/ 目录不存在时 → 先执行机制 step 2 初始化目录

不记录:
  - 简单的语法修正（拼写、标点）
  - 用户明确表示不需要记录

存储位置: {项目根}/.issues/ 或 {项目根}/docs/issues/   # 按 trigger-mechanism.md §三 位置解析，初始化时固定
目录结构: {位置}/{YYYY}-{MM}-{DD}-{HH}-{MM}-{SS}/
文件命名: "{标题}-{严重等级}.md"

严重等级: critical | high | medium | low      # 与 ERROR/ 一致

标题规范:
  - 去除文件名非法字符（斜杠、反斜杠、冒号、星号、问号、双引号、尖括号、竖线等）
  - 空格替换为 _
  - 保留 - 专作「标题」与「等级」的分隔符

内容要素:                                     # 格式由 AI 决定，记录须详细
  - 标题、严重等级、发生时间
  - 问题描述（现象、报错、影响范围）
  - 复现步骤
  - 根本原因
  - 解决方案
  - 样例（修复前后对比 / 输入输出 / 代码片段）
  - 环境信息（OS、工具/框架版本、项目上下文）
  - 标签

检索: 出现问题先查 .issues/ 与 ERROR/，参考但不盲从
初始化: 目录不存在时创建 {位置}/ + README.md（模板见 trigger-mechanism.md §六），并写入本项目的位置解析结果
```

推荐模板骨架（可按问题特性调整）:

```markdown
---
title: {问题标题}
severity: critical | high | medium | low
status: resolved
created: {YYYY}-{MM}-{DD} {HH}:{MM}:{SS}
tags: [{标签}]
---

## 问题描述
{现象、报错、影响范围}

## 复现步骤
1. ...
2. ...

## 根本原因
{诱因分析}

## 解决方案
{具体做法、关键改动}

## 样例
{修复前/后对比、输入输出、代码片段}

## 环境信息
{OS、工具/框架版本、项目上下文}
```

> 职责边界（与 `ERROR/` 分离，不双写）:
> - `.issues/` ＝ **项目级**，记录项目本身的 bug 事实，随项目走，面向团队/未来维护者
> - `ERROR/` ＝ **规则库级**，记录 AI 跨项目经验与行为纠正，存于 `D:\Code\.Rules\ERROR/`，给 AI 跨会话用
> - 项目 bug 归 `.issues/`；AI 被纠正的行为 / 可复用经验归 `ERROR/`

### 9.5 项目审计查阅 (audit)

> 定期扫描各项目发现的健康待办（文档同步、git 卫生、版本矛盾等），集中存于 `D:\Code\.Rules\docs\audit\`。机制详见 `docs/audit/README.md`。

```yaml
AI 查阅约定（进入任何业务项目会话时）:
  1. 检查 D:\Code\.Rules\docs\audit\{项目名}\ 是否有 status: open 条目
  2. 按 level 排序，P0/P1 项主动告知用户并建议本会话处理
  3. 处理完成后将条目标记 resolved 并填日期

三系统边界（职责分离，NEVER 双写）:
  - ERROR/       : AI 跨项目经验 / 行为纠正（给 AI 跨会话）
  - .issues/     : 项目本身的 bug（随项目走，给团队）
  - docs/audit/  : 扫描发现的项目健康待办（给开发者批量处理）

原则:
  - 规则细节一处定义（本节 + docs/audit/README.md），NEVER 在各项目 CLAUDE.md 重复
  - 各项目 CLAUDE.md 仅保留一行指针（指向 audit 目录）以提升可见性，不复制规则
```

## 十、信息持久化

> AI 通过联网搜索、MCP 工具等外部调用获取的信息，必须持久化存储，避免跨会话丢失。

### 10.1 触发条件

```yaml
触发场景:
  - 使用 WebSearch / WebFetch 等联网搜索工具获取信息后
  - 使用 MCP 工具（如 ref_search_documentation、webReader）获取外部信息后
  - 其他从外部源获取有价值信息的操作后

不触发:
  - 仅查询本地文件、代码搜索
  - 工具调用失败、未返回有效内容
  - 获取的信息仅用于当前操作的简单判断（如版本号比较），无参考价值
```

### 10.2 存储规则

```yaml
存储位置: {项目根目录}/information/
文件命名: {信息主题}-{YYYY-MM-DD}.md
编码: UTF-8

命名示例:
  - "Flutter-3.27新特性-2026-04-21.md"
  - "React-Server-Components最佳实践-2026-04-21.md"
  - "FastAPI-Pydantic-v2迁移指南-2026-04-15.md"

命名要求:
  - 信息主题: 简洁概括内容，用 - 分隔词语
  - 获取日期: 当天日期，格式 YYYY-MM-DD
  - 避免过长文件名（建议 ≤ 80 字符）
```

### 10.3 文件格式

```markdown
# {信息主题}

**获取日期**: YYYY-MM-DD
**信息来源**: {搜索关键词 / URL / 工具名称}
**相关上下文**: {为何需要此信息}

---

{获取的关键信息内容，整理为易读的 Markdown 格式}

---

## 关键要点

- 要点1
- 要点2
- 要点3
```

### 10.4 执行要求

```yaml
流程:
  1. 判断获取的信息是否有持久化价值
  2. 提取信息主题，生成文件名
  3. 检查 information/ 目录是否存在，不存在则创建
  4. 检查是否已有同名文件（仅日期不同），如有则合并或更新
  5. 按格式写入文件
  6. 简短告知用户: "已保存到 information/{文件名}"

原则:
  - 整理后再存储，NEVER 直接粘贴原始工具输出
  - 提取与当前任务相关的核心信息，去除噪音
  - 同一主题同一天的信息合并为一个文件，不重复创建
  - 存储操作不阻塞主任务流程
```

## 十二、改动文档生成

### 12.1 触发条件

满足以下任一条件时，AI **主动询问**用户是否生成改动文档：

- **版本号迭代**时（修改 version 字段，或 commit message 含版本号）— 最可靠：AI 自己就是改版本号的人
- 本次会话已执行 **3+ 次 git commit** — commit 是离散事件，比"文件修改次数"更易感知
- 用户**表示完成一批工作或切换话题**时（如"先这样吧""换个事"）
- 用户**主动要求**生成时（立即执行，不等触发条件）

> 触发条件必须是 AI 在当前轮次能直接感知的事件，NEVER 依赖跨轮计数（如"修改达 N 次"）。
> 询问格式："检测到 {触发事件}，是否生成改动文档？"

### 12.2 条目格式

改动文档按「Bug 修复」和「功能更新」两类分别记录：

#### Bug 修复条目

```markdown
### [Bug 名称]

**Bug 描述 / 现象**：[什么表现、何时触发、影响范围]

**根本原因**：[为什么会出现]

**解决方案**：[整体思路]

**改动细节**：
- `文件路径:行号范围` — [改了什么、为什么这么改]
- `文件路径:行号范围` — [改了什么、为什么这么改]
```

#### 功能更新条目

```markdown
### [功能名称]

**如何使用**：[用户视角的使用方式]

**利弊分析**：
- 利：[带来了什么价值]
- 弊 / 权衡：[代价、限制、已知问题]

**改动细节**：
- `文件路径` — [新增 / 修改了什么]
- `文件路径` — [新增 / 修改了什么]
```

### 12.3 文档整体结构

```markdown
# 改动文档 — {项目名} {版本号}

> 生成时间：{YYYY-MM-DD}　|　涉及修改：{N} 次

[功能条目 ...]

## Bug 修复

[Bug 条目 ...]

## 其他改动

[重构 / 配置 / 依赖等，简要说明]
```
