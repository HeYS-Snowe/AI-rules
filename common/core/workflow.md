## 三、编码实现阶段

### 3.1 开发流程

```yaml
分支策略:
  main: 生产环境，受保护
  develop: 开发环境
  feature/*: 功能分支
  fix/*: 修复分支
  release/*: 发布分支

开发步骤:
  1. 从 develop 创建 feature 分支
  2. 编写代码 + 单元测试
  3. 自检代码质量
  4. 提交 Pull Request
  5. 代码审查
  6. 合并到 develop
```

### 3.2 提交规范

```yaml
格式: <type>(<scope>): <subject>

类型 (type):
  - feat: 新功能
  - fix: Bug 修复
  - refactor: 重构
  - style: 代码格式
  - docs: 文档
  - test: 测试
  - chore: 构建/工具
  - perf: 性能优化

示例:
  - feat(auth): add JWT token refresh
  - fix(api): resolve timeout issue in user service
  - refactor(user): extract validation logic
  - docs(readme): update installation guide
```

### 3.3 代码审查清单

```markdown
## 代码质量
- [ ] 代码符合项目规范
- [ ] 命名清晰有意义
- [ ] 无重复代码
- [ ] 无魔法数字

## 功能实现
- [ ] 实现符合需求

- [ ] 错误处理完善

## 测试
- [ ] 单元测试覆盖

## 安全
- [ ] 无安全漏洞
- [ ] 敏感数据处理正确

## 性能
- [ ] 无明显性能问题
- [ ] 资源使用合理
```

## 四、测试验证阶段

### 4.1 测试层次

```yaml
单元测试:
  范围: 工具函数、业务逻辑、状态管理
  覆盖率: 核心逻辑 ≥ 80%
  命名: test_<method>_<scenario>_<expected>

集成测试:
  范围: API 接口、数据库操作、外部服务
  数据: 使用测试数据库/Mock

端到端测试:
  范围: 关键用户流程
  工具: Appium / Flutter Integration Test
```

### 4.2 测试结构 (AAA 模式)

```dart
test('getUser returns user when user exists', () async {
  // Arrange - 准备
  final mockRepository = MockUserRepository();
  final service = UserService(mockRepository);
  const userId = 'user-123';
  final expectedUser = User(id: userId, name: 'John');

  when(mockRepository.findById(userId))
      .thenAnswer((_) async => expectedUser);

  // Act - 执行
  final result = await service.getUser(userId);

  // Assert - 断言
  expect(result, equals(expectedUser));
  verify(mockRepository.findById(userId)).called(1);
});
```

## 五、构建打包阶段

### 5.1 构建流程

```yaml
环境检查:
  - 依赖版本正确
  - 环境变量配置
  - 构建工具可用

构建执行:
  - 清理旧产物
  - 编译/打包
  - 资源优化
  - 代码混淆 (Release)

产物命名:
  格式: {项目名}_{状态}_{版本}_{日期}_{序号}

  状态类型:
    完全体:
      - release: 正式版
      - fix: 修复版
      - hotfix: 紧急修复

    非完全体:
      - alpha: 内测版
      - beta: 测试版
      - rc: 候选版
      - dev: 开发版
      - debug: 调试版

  示例: MindCareAI_release_1.0.0_20250312_01.apk
```

### 5.2 构建后处理

```yaml
自动处理:
  1. 调用版本管家 (version-manager agent)
  2. 重命名构建产物
  3. 备份原始文件到 backup/
  4. 生成构建日志
  5. 记录构建历史

构建产物:
  - APK/AAB (Android)
  - IPA (iOS)
  - Web 包 (Web)
  - Docker 镜像 (后端)
```

## 九、错误记录流程

> 引用: `errors/README.md`

### 9.1 主动记录触发条件

AI 在以下情况**主动记录**错误，无需用户指令：

```yaml
触发场景:
  - 解决了一个有价值的错误后
  - 踩了一个之前踩过的坑
  - 发现了值得记录的配置/环境问题
  - 遇到了复杂的多步骤排查过程

不记录:
  - 简单的语法错误
  - 明显的拼写错误
  - 一次性环境问题
```

### 9.2 记录流程

```yaml
步骤:
  1. 在 errors/entries/ 下创建新的 .md 文件
  2. 按模板填写内容 (见 errors/README.md)
  3. 更新 errors/ERRORS_INDEX.md 索引
  4. 简短告知用户: "已记录到错误知识库 ✅"
```

### 9.3 错误记录模板

```markdown
---
title: 错误名称
type: compile | runtime | logic | config | dependency | other
tech_stack: 技术栈
tags: [tag1, tag2, tag3]
severity: critical | high | medium | low
first_seen: YYYY-MM-DD
last_seen: YYYY-MM-DD
occurrences: 1
references:
  - https://...
---

## 错误描述
{报错信息、截图、现象等}

## 复现步骤
1. 步骤一
2. 步骤二

## 解决方案
{具体解决步骤}

## 原因分析
{为什么会出现这个错误}

## 预防措施
{下次怎么避免}
```

### 9.4 错误更新流程

当再次遇到相同错误时：

```yaml
操作:
  1. 找到对应的 .md 文件
  2. 更新 last_seen 日期
  3. occurrences + 1
  4. 如有新发现，补充内容
```

### 9.5 错误分类

| 类型 | 说明 | 示例 |
|------|------|------|
| compile | 编译错误 | 类型不匹配、语法错误 |
| runtime | 运行时错误 | 空指针、循环依赖 |
| logic | 逻辑错误 | 条件判断错误、计算错误 |
| config | 配置错误 | 环境变量、配置文件 |
| dependency | 依赖错误 | 版本冲突、包缺失 |
| other | 其他 | 环境问题、工具问题 |
